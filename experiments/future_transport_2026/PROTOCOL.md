# Prospective Future Transportation experiment protocol

Status: **prospective design locked before production; zero qualifying runs have been accepted**. This file records the analysis decisions before any new production outcome is inspected. Technical pilot outcomes were inspected to verify implementation and motivated the disclosed radio-calibration cohort below; every pilot is excluded from estimation. The historical 140-run and 90-run data underlying the manuscript are absent from the public checkout. New experiments are a separate cohort, and all old result tables and figures must be replaced after execution.

## Research question and scope

In the specified ns-3 NR sidelink + SUMO intersection and emergency-warning scenarios, how do communication treatments change application-level CAM availability, the controller's observed action, and the recorded simulated collision outcome? This is a simulation study of these implemented models. It cannot estimate deployed-vehicle safety without external sensor, channel, and controller validation. The Sionna on/off contrast compares two implemented propagation pipelines; it does not isolate ray tracing alone because spectrum fading changes too.

## Locked design before production execution

Two simulation campaigns use a fixed SUMO road layout and routes per campaign. The emergency-warning power series uses the exact 14 prespecified `txPower` levels −20, −15, −12, −9, −6, −3, 0, 3, 6, 9, 12, 15, 18, 20 dBm. Ten complete random blocks run every level, giving 140 runs. Sionna is disabled in this campaign. The treated variable is NR UE PHY power in dBm. The outcome definitions are whole-run PRR and first eligible receiver CAM reception, including right-censored receivers.

The intersection series uses thirty complete paired random blocks and five arms: radar-only (CAM and CPM off), Sionna with 0 dB additional receiver noise figure, Sionna with 53 dB additional receiver noise figure, native propagation with 0 dB additional receiver noise figure, and native propagation with 53 dB additional receiver noise figure. Transmitter `txPower` is 23 dBm in all five arms. The implemented `equiv_tx_power_dbm` profile sets the effective receiver noise figure to `max(0, base_noise_figure_db + txPower - equiv_tx_power_dbm)`; values 23 and -30 dBm yield 0 and 53 dB additional noise figure, respectively, with the observed 5 dB base. The simulator log must verify both the base and effective values for each run. These are controlled stress levels, not field-calibrated channel conditions. The same road geometry, routes, SUMO time step, controller thresholds, CAM policy (other than radar-only), logging, and random block identifiers are used across arms. A separate pilot confirms command-line compatibility, clocks, file completeness, and channel audit operation; its outcomes are excluded from production estimates. Do not tune treatment or controller thresholds in response to pilot collisions.

If Sionna is run in its published example circle scene, the intersection analysis cannot claim geometry-specific propagation for the SUMO road map. A co-registered scene is required for the Sionna comparison. Check antenna placement and ray-path plausibility at prespecified positions on the intersection before the first qualifying run. Every scene, materials file, patch, solver argument, update threshold, frequency, and image digest belongs in the manifest.

## Unit of analysis and event semantics

The NR sidelink configuration is fixed at `centralFrequencyBandSl=5.89e9` Hz, `bandwidthBandSl=400` in the simulator's 100-kHz units (40 MHz), and `numerologyBwpSl=2`. The CcBwpCreator operation-band constructor receives the converted value 40e6 Hz; the sidelink BWP configuration retains 400 units. For this configuration, the PHY must report 40 MHz and 53 resource blocks after preconfiguration. Each run records and validates both operation-band and PHY values. The Sionna scene is configured at the same 5.89-GHz center and 40-MHz bandwidth. Earlier pilots with inconsistent operation-band metadata are excluded; all production runs use the corrected source.

A run is the replication unit. `RngSeed`, `RngRun`, ns-3 stream assignments, SUMO seed, sensor stream assignments, and Sionna seed are explicit manifest fields; sharing only `RngRun` does not prove paired exogenous inputs. Verify pre-intervention trajectories against logs. If they differ, report that matching failed and use an analysis without paired claims.

For a CAM transmission, use the pair `(tx_id, cam_gdt_ms)` only within the <65.536 s non-wrapping observation window; reject duplicate identities. The existing `pkt_uid=-1` in CAM logs is not a real packet UID. Preserve separate labels for native PHY traces, application reception, injected GeoNet rejection, inferred CAM silence, and absent application reception. A missing reception is not a confirmed PHY failure. Application-level PRR for veh2→veh3 is the number of unique successful receptions divided by eligible veh2 CAM transmissions in the fixed complete-link observation window. In radar-only, PRR is undefined. Report each run's numerator and denominator. A separate legacy MetricSupervisor estimator may be calculated but must be named distinctly.

First CAM reception is the first application arrival, measured from scenario start and, separately, from first receiver eligibility. Unreceived first events are right-censored at completed run horizon, never filled with the horizon as an event. First controller action is `min(first_cam_reaction, first_sensor_reaction)` over observed command records. Record each source separately and preserve absence. Also retain sensor observation records and label the radar-like sensor as a SUMO-state-based model.

## Run validity and analysis

A run qualifies only after a successful simulator exit at the planned horizon, a complete execution manifest, valid and monotone logs, matched application receptions to actual transmissions, the expected vehicle IDs, and a parseable collision logger. Missing or malformed collision XML means unknown outcome, not zero collisions. Preserve failed runs and reasons. Verify the collision pair and distinguish any other collisions. Record Sionna fallbacks, zero/invalid responses, and no-path conditions; reject an unexplained fallback from the qualifying cohort rather than treating it as a physical loss sample.

Estimate collision proportions with two-sided 95% Wilson intervals and show discordant paired-block counts for between-arm comparisons. Bootstrap complete seed blocks for uncertainty in paired contrasts and power curves. Do not treat packets or 19 receivers from one run as independent replications. For first-reception P90, use a stated censoring-aware estimator and report it as not estimable if the survival curve does not cross 10%. State every quantile's observation and censoring counts. Spearman correlations are descriptive; any inferential interval or permutation test must preserve the seed-block structure. Publish run-level data, unsuccessful runs, exact commands, input hashes, software revisions, and figure-generation scripts.

Primary results include effect sizes with uncertainty even when null or adverse. Temporal event chains do not establish that a specific missed CAM caused a collision. Any such claim requires controlled packet-level replay with identical exogenous inputs; otherwise the paper must limit causal language to treatment contrasts under the simulation model.

## Pilot-stage amendment, 17 September 2026

The first emergency technical pilot used the source-default 0.01 s SUMO step and transmitted both CAM and CPM. It remains excluded from estimation. Before any qualifying run, the emergency campaign was fixed to the repository's 20-vehicle V2V map and route for 100 s, with 0.05 s SUMO/TraCI updates, all 20 vehicles equipped, CAM on, CPM off, and local sensor reaction off. Disabling CPM confines the power-sweep outcome to CAM availability and CAM-based control; the 0.05 s step reduces the cost of a 100-s simulation. The 14 power levels, route, controller thresholds, and acceptance criteria were not selected from pilot outcomes. A second technical pilot must validate this amended configuration and is also excluded from estimation.

For the emergency CAM analysis, the sender is `veh2` (`Car0`) and there are 19 possible receivers. A transmission-receiver pair is eligible if both vehicles are present in the nearest preceding 0.05-s SUMO netstate snapshot and their Euclidean separation is at most 150 m. Lane positions are projected onto the `net.xml` lane polylines; there is no temporal interpolation. Successful application receptions are joined to the latest preceding CAM with matching transmitter station ID and `generationDeltaTime`, requiring at most 1 s delivery latency. Report the per-run eligible-pair numerator and denominator, and compute uncertainty across independent seed blocks rather than treating pairs as replicates.

For the 100-s emergency run, `generationDeltaTime` wraps after 65.536 s. Join CAM transmission and reception by station ID, generationDeltaTime, and the transmission-time wrap epoch; reject any remaining duplicate identity. The non-wrapping two-field rule above applies to the 20-s intersection campaign only.

The intersection ray-tracing scene uses disclosed triangle meshes in the SUMO local XY frame. Two idealized building blocks and vehicle bodies are assigned ITU concrete/metal materials, with a medium-dry-ground plane. These are modeling assumptions, not surveyed geometry. The scene manifest records every mesh hash. Sionna path gain is derived from the narrowband coherent sum of valid complex ray coefficients. When no valid ray is returned for a directed pair, the server sends its explicit 300 dB no-ray sentinel; this is a computational convention, not a measured physical path loss. Count such responses and report their fraction of path-gain requests for every Sionna run and arm. GPU execution uses OptiX libraries extracted from NVIDIA Linux driver 615.71.09 and mounted read-only in the research container; the Windows driver is 616.56. The driver-branch mismatch is an environment limitation, and WSL wall-clock times should not be presented as native-Linux performance benchmarks.

## Radio-calibration cohort added before production

The behavioral pilot showed that whole-run PRR changes when a controller action prevents a collision: the vehicles then follow different trajectories, so subsequent CAM exposure differs. Accordingly, whole-run PRR in the behavioral intersection cohort is descriptive and cannot establish a channel-quality contrast. A separate, matched radio-calibration cohort disables CAM-triggered and sensor-triggered controller reactions while retaining CAM transmissions. It repeats the four active-CAM channel/receiver-penalty arms at the same 30 seed blocks, with the same routes and a 20-s simulation horizon. Its primary application-level veh2-to-veh3 CAM PRR is counted over the fixed approach interval [2.0, 5.0) s, before the nominal junction conflict. Every calibration run must verify identical pre-conflict SUMO trajectories across the four arms. Radar-only has no CAM denominator and is excluded from this cohort. These 120 runs are distinct from the 150 behavioral runs; calibration outcomes are not used to adjust treatment settings or controller thresholds.
